## 28.11.2026 — синхронизация производства карты и объектов (решение владельца)

Карта и ZPB/другие производители моделей работают параллельно. Незавершённые здания и объекты не блокируют производство рельефа, дорог, масок и прочих независимых слоёв. Расширить существующие CC03 Sector Manager, CC04 Config/Asset Manager и контракты sector package; не создавать отдельный сервис или новый фреймворк. Ниже целевой контракт, не заявление о реализованном механизме.

### Два связанных реестра, один версионированный snapshot
- Asset registry: стабильный asset_id, категория/семантический тип, варианты, владелец, версия/хеш, относительный P3D resource path (A3-first by reference или согласованный собственный namespace), зависимости/CfgPatches/DLC/права, габариты, footprint, origin/pivot, базовая ориентация, допустимые масштаб/поворот, правила контакта с землёй, validation evidence. Статусы MISSING → DRAFT → VALIDATING → VALIDATED → PUBLISHED; INVALID/RETIRED отдельные состояния. Путь/имя файла не является стабильным ID. Изменённый хеш требует нового validation, прежняя принятая версия сохраняется до успешной публикации. Не копировать чужие игровые ресурсы в мод.
- Placement registry: стабильный placement_id, source feature ID + provenance/epoch или детерминированный procedural ID; semantic_type, asset_id или unresolved requirement_id, pinned asset_version, CRS/world origin, координаты, высотная привязка (relative/absolute явно), yaw/pitch/roll/scale, известный контур/габарит/ограничения, owning sector, status, manual override + lock. Не додумывать неизвестную этажность/контур. Хранить требуемые размещения даже до готовности модели: PENDING_ASSET не теряется при перегенерации. Прокси/placeholder только в отдельном явно помеченном editor-only слое; не считать заменой достоверного объекта или production PASS.
- Один авторитетный реестр логических размещений на весь мир, не независимые списки истины в каждом TB-секторе. Sector core/halo с детерминированным владельцем по anchor; габарит и зависимости могут затронуть соседние сектора, но один placement_id импортируется один раз. Согласованные snapshots для GRM, TB и QC; сборка не читает незавершённые версии модели. Отдельно локальные реальные геоданные/модели/артефакты и GitHub-код, схемы, лицензии, метаданные/redacted evidence; не публиковать бинарники без отдельного разрешения.

### Валидация и запросы на добавление/обновление
1. Производитель передаёт manifest кандидата, его immutable version/hash, зависимости и результаты нативной проверки Object Builder/Buldozer (geometry/LOD/materials/paths, pivot, footprint/границы, масштаб, ориентация, контакт с землёй; специализированные building/path/roadway/fire geometry gates по типу). Наличие файла само по себе не PASS; model gate и world-placement gate независимы. WRP/PBO build и реальные размещения остаются под существующими owner gates.
2. Запрос владельца/конвейера ADD/REPLACE/RETIRE содержит request_id, asset_id/version или semantic type, область (явный список placements, сектор, географический фильтр или whole-world), правила выбора/вариантов, expected registry revision. Сначала dry-run: pending/resolved/affected/locked/conflicts, старые и новые зависимости, затронутые core+halo; неоднозначные соответствия остаются unresolved. Не заменять все похожие здания произвольно. Whole-world означает поиск по реестру всей карты, а не обязательный полный rebuild.
3. Только VALIDATED candidate и согласованный запрос могут создать новый snapshot; atomic publication/compare-and-swap revision, идемпотентность request_id, журнал операций и откат к принятому snapshot. Сохранять существующие placement_id/позиции/manual locks, если запрос явно не меняет геометрию; при изменении pivot/footprint пересчитать посадку и занятость, соседние зависимости, проверить дороги и пересечения, не переносить объекты молча.
4. Reverse dependency index asset_id/version → placement_id → owning/affected sectors. Пересобрать только изменённые object layers и действительно зависимые маски/дороги/материалы, не трогать GM heights/imagery без доказанной зависимости. Отдельные выходы и staging copy, один writer для TB project, не редактировать одновременно с агентом зданий. Native import/update + export/readback ID-to-pose manifest, отсутствие дублей/потерь, контроль изменений вне запроса, визуальные контрольные точки и RPT. После PASS принятие нового snapshot; при FAIL прежний принятый пакет остаётся доступен, причина и очередь retry сохранены.
5. Асинхронно по готовности производителей, синхронно по версии при сборке: ручной конечный запуск очереди по запросу, без фонового сервиса. На каждую сборку фиксировать версии реестра и asset manifest; новые поступления не меняют уже запущенную сборку. Готовность показывать раздельно: terrain/imagery/roads/vegetation, coverage pending assets, model validation, actual placement validation. Неготовое здание не блокирует независимый слой, но блокирует полную приёмку соответствующего объектного слоя.

### Первый gate (Pipeline v0.1, только ограниченный synthetic editor-only)
Сначала переиспользовать нативный GRMAUTO04 и текущие CC03/CC04. На отдельной копии и без новых чужих P: writes доказать: (A) запись незавершённого здания сохраняется между перезапусками без реальной модели; (B) публикация разрешённого контрольного ассета после validation разрешает нужные записи по stable ID, включая два соседних core; (C) повтор одного request_id не создаёт дубликаты; (D) отклонённая версия, неверная зависимость, пересечение границы, изменение pivot/габарита, ручной lock и откат не повреждают принятый snapshot; (E) unaffected terrain/imagery/object hashes и native pose readback неизменных размещений совпадают, Buldozer подтверждает вставленные объекты. Для тестов используются законно доступные контрольные модели/синтетические записи, не готовые реальные здания. Не начинать реальные массовые размещения до согласования extent, источников, profiles, model gates и scope. Stage001 PARTIAL, no WRP/PBO build, merge or stage promotion.
